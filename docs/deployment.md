# Hosted synthetic demo

The demo uses Vercel for the Next.js UI and a dedicated Convex Cloud project for authentication, synthetic records and workflows. All financial work remains simulated. Each visitor receives an anonymous authenticated identity and an isolated workspace. New visitors start with Demo; the Dataset selector also offers Company History and Evaluation.

Current deployment:

- Demo: https://attest-demo-lemon.vercel.app/work
- Vercel project: `attest-demo` in `landon-trinhs-projects`.
- Convex project: `attest-demo` in `landon-trinh`.
- Production backend: https://rightful-spider-558.convex.cloud
- Development backend: https://utmost-stork-409.convex.cloud

The initial release was uploaded from this workspace with the Vercel CLI. Automatic Git deployments are not connected. To deploy later changes from the linked workspace, run `npx vercel deploy --prod`; the production deploy key is stored in Vercel's environment settings. `.env.local` selects the cloud development backend for local commands; it does not contain the production deploy key.

## Connect the accounts

Use Node 22 or newer and run `npm ci` from the repository root. Connect Convex with:

```sh
npx convex dev --configure --dev-deployment cloud --once
```

Complete browser sign-in and select or create the project's dedicated demo backend. This writes ignored local deployment settings. Keep existing production data in a separate project.

Import this repository and the branch containing the hosted-demo changes into Vercel as a Next.js project. The root directory is the repository root. `vercel.json` supplies the build command:

```sh
npx convex deploy --cmd 'npm run build' --cmd-url-env-var-name NEXT_PUBLIC_CONVEX_URL
```

The Convex CLI supplies `NEXT_PUBLIC_CONVEX_URL` during the build, so the browser connects to the backend deployed with that version of the app. Do not build the hosted UI with a localhost backend URL.

## Configure the hosted backend

Create the demo project's production deployment in the Convex dashboard. Generate its production deploy key with deployment permission and store it as `CONVEX_DEPLOY_KEY` in Vercel's **Production** environment. Keep the key in service settings, never in source control or browser-visible variables. Preview deployments need their own Convex preview key and settings if enabled; do not use the production key for previews.

Set these variables on the **Convex production deployment**:

| Variable | Value / purpose |
| --- | --- |
| `ATTEST_HOSTED_DEMO` | Exactly `true`; enables synthetic dataset selection/reset and starts new visitors in Demo. Unset or any other value leaves cloud dataset loading disabled. |
| `SITE_URL` | The final Vercel production URL. |
| `JWT_PRIVATE_KEY` | Private signing key generated for this deployment by Convex Auth setup. |
| `JWKS` | Matching public verification keys generated by Convex Auth setup. |

For a new deployment, use the official authentication setup once:

```sh
npx @convex-dev/auth --prod
npx convex env set --prod ATTEST_HOSTED_DEMO true
```

Use the Vercel production URL when prompted for the web-server URL. The app already contains `convex/auth.ts`, `convex/auth.config.ts` and auth HTTP routes. Preserve those files. Do not regenerate keys on ordinary redeploys: existing sessions depend on them. `scripts/setup-local-auth.mjs` deliberately rejects production and must not be used for this step.

CREAO, Moss and Apify keys are not needed for the deterministic demo. If live integrations are enabled later, configure their credentials separately on Convex. Live invoice investigation and live policy learning use separate agent IDs; a failed live run must never be silently converted to simulation.

## Publish and verify

Deploy the configured branch to Vercel's production environment. The build deploys the Convex functions and schema and builds the Next.js UI. No database import or CLI seed is needed: the UI loads the checked-in synthetic fixtures for each authenticated visitor. The local seed/evaluation commands intentionally remain local-only.

Before publishing, run:

```sh
npm run typecheck
npm test
npm run build
```

After publishing, verify the actual hosted URL:

1. Open `/work` in a fresh browser session. It should sign in automatically and show Demo with three cases.
2. Check `INV-TEAM-001`: $20,000 supported gross, a $3,000 deposit, $17,000 remaining due and a $1,000 discrepancy.
3. Select Company History (eight cases), then Evaluation (six). Reload and confirm the selection persists.
4. Open a second private browser session and confirm it receives its own Demo workspace.
5. Walk through an approval and simulated posting. Select Internal Auditor and confirm modification attempts are denied and audited.
6. Reset the active dataset and confirm it returns to its starting records while the old generation remains archived and the other visitor is unaffected.
7. Open a case URL directly and reload it to verify Next.js routing on the host.

Local tests and a successful build do not establish that hosted authentication or workflows work. Record live verification only after exercising the deployed app.
